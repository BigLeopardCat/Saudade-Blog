# 聊天完成与持久化

登录用户的 `/api/chat/stream` 保持标准 SSE 具名事件协议：`text` 可逐步显示，`done`
表示上游成功结束，且本轮已收到的回复、执行回执和待确认状态保存成功。访客不创建聊天记录。
非流式接口在相同保存条件满足后返回 `success: true`。

## 保存顺序

- `receipts` 到达时立即保存。一个回执批次及其待办状态更新使用同一短事务，失败则整批回滚。
- 收到上游 `done` 后保存完整助手正文，成功后才向浏览器转发 `done`。
- 收到上游 `error`、格式错误或提前断流时，不将残缺正文保存成完整助手消息。
  已经提交的执行回执保留，不能因回答失败而撤销已发生的业务事实。
- 摘要是派生缓存，使用单调消息边界防止旧值覆盖新值。摘要保存失败保留旧摘要并告警，
  不撤销已保存的完整回复。

## 取消与失败

`chat::persistence` 使用 Tokio task 执行短写入，正常请求等待该任务完成并检查结果。
浏览器在写入期间断开时，只取消 HTTP 等待方，已开始的写入继续完成；任务自身记录带 trace ID
的失败。数据库或任务错误不会变成 `done`，也不向浏览器暴露数据库异常原文。

本地聊天记录的保存失败不能证明远端操作失败。界面提示用户先核对结果、避免重复执行，
服务不自动重试写入。Python 的持久执行账仍负责业务操作的幂等与未知结果处理；博客记录是
展示与检索副本。这不构成跨服务 exactly-once，也不保证进程崩溃后恢复尚未提交的副本写入。

## 回归范围

- MockDatabase 验证回复插入失败、回执批次回滚及 SSE 终止事件。
- Tokio 通道验证等待顺序和等待方取消后写任务继续执行。
- CI 的 PostgreSQL 服务验证真实事务回滚，以及回复失败不丢失已提交回执。
- 无需真实模型、生产账号或生产数据库。
