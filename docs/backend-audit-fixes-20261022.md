Argon2 运算统一进入 `spawn_blocking`，最多同时运行 4 个密码任务，超过时返回繁忙，避免占满 Tokio I/O 工作线程或无限排队。自助改密、旧密码哈希升级增加旧哈希与 token_version 条件，避免异步计算期间覆盖已经更新的凭据。

**限流行为变化：** `LOGIN_MAX_ATTEMPTS` 现在计所有凭据尝试，包括成功和在途请求，成功后不清空窗口；仍沿用 `LOGIN_WINDOW_SECS` / `LOGIN_LOCKOUT_SECS`。同 IP 总量为 `max(LOGIN_MAX_ATTEMPTS × 10, 20)`。三个凭据入口共享计数，`.env.example` 已同步。多副本部署时该内存计数仍是每进程独立的。

## 已处理的数据加载与性能问题

1. **聊天图片在读入后才裁剪。** 原实现先拉最近 50 条消息的全部 dataURL，再裁成 8 MiB；响应受限，但数据库传输和后端内存未受限。现在先查图片 ID/字节数，计算保留的完整消息集合，再仅读取选中图片的 data 大字段。第二次按第一步的图片 ID 查询，避免两步之间新插入的图片突破预算。保留原有“从最新开始，放不下的消息及更早消息不带图”的语义。新增真实库用例中，50 条各 256 KiB 的图片只读取最新 32 条的图片正文；单元用例另外验证整条超预算时只查元数据、不发正文查询。
2. **默认会话解析读取整行历史。** 现在只取 `conversation_id`，不再加载不需要的历史正文。
3. **无关键词文章筛选读取全部正文后又清空。** 分类/标题筛选改用已有 `NoteSummary` 投影，响应字段和可见性规则保持一致；真正的关键词搜索仍需要正文参与匹配和评分。
4. **会话搜索标题定位 N+1。** 对每个标题命中的会话分别读取首条消息，最多产生 200 次串行往返。改成一次 `GROUP BY conversation_id + MIN(id)`，同时仅取会话 ID 和消息 ID。
5. **默认会话查询缺少匹配索引。** 新增 `(user_id, id DESC) INCLUDE (conversation_id)`，并接入 `ci_schema_files.py` 的唯一建库清单。

索引效果使用隔离库的 50,000 条合成消息验证：前 25,000 条属于用户 A，后 25,000 条属于用户 B，查询 A 的最新消息。原方案倒扫主键、过滤 25,000 行；增加索引后是 Index Only Scan、Heap Fetches=0。

| 单次 EXPLAIN ANALYZE | 原索引方案 | 新索引 |
| --- | --- | --- |
| 缓存页访问 | 1,528 | 3（1 hit + 2 read） |
| Execution Time | 26.945 ms | 0.161 ms |

这些数值只描述本次合成数据、缓存和主机负载下的执行计划，不是线上接口延迟承诺或整体吞吐量测试。

## 仍存在的规模风险

- `/api/public/notes/search`、公开说说/留言、评论列表及聚合搜索仍有全量结果路径。文章正常列表已分页，作者/标签/统计也已有批量查询，不能把所有列表都误判成 N+1。继续优化全量接口需要同时设计客户端分页、排序、总数与 agent 读取协议；本次没有悄悄截断现有结果。
- 包含 `%keyword%` 的正文/评论搜索仍可能扫描大量文本；现有预筛减少了传输，但不等于全文索引。应先用实际数据量和常用关键词测 `EXPLAIN (ANALYZE, BUFFERS)`，再选择 pg_trgm 或全文检索，不能直接替换而改变中文分词、大小写及排序语义。
- 一部分查询错误仍通过 `unwrap_or_default` 转为空列表，前端可能把数据库故障看成“没有数据”。需要按接口逐步统一失败协议和观测；本次未批量改变现有错误信封。
- 部分请求会重复校验用户并读取角色/站点信息；这是额外查询，但目前没有线上慢请求分布，尚不能判定其收益高于缓存失效和权限收回的复杂度。
